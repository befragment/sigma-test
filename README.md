# Табель смен по фото из Telegram

Сервис автоматически заполняет табель смен по сообщениям из рабочих Telegram-групп. Фото с подписью, опубликованное
в группе в окне заступления на смену, превращается в отметку `1` в табеле на дату смены. Спорные случаи уходят
на ручную проверку оператору. Каждое фото из группы попадает в журнал со статусом и причиной; у супергрупп —
ещё и со ссылкой на исходное сообщение. Табель за месяц выгружается в xlsx в формате листа «Табель» из ТЗ
(`docs/task.xlsx`).

Бот в чате ничего не пишет: результаты обработки, ручная проверка и табель доступны только через HTTP API.

Отчёт о выполнении задания, включая проверку на реальном Telegram-боте, — [REPORT.md](REPORT.md).

Стек: Python 3.12, FastAPI, aiogram 3 (long polling), PostgreSQL, SQLAlchemy 2 (async) + asyncpg, openpyxl.
Один процесс: lifespan FastAPI запускает поллинг ботов и N воркеров обработки как фоновые asyncio-задачи.

## Запуск

```bash
cp .env.example .env          # задать ADMIN_TOKEN и BOT_TOKENS
docker compose up -d --build  # app на http://localhost:8000, postgres на localhost:5432
curl localhost:8000/health    # {"status":"ok"}
```

Схема БД создаётся при старте (`Base.metadata.create_all`) — упрощение первой версии вместо миграций.
Swagger: http://localhost:8000/docs.

| Переменная          | По умолчанию | Назначение |
|---------------------|--------------|------------|
| `DATABASE_URL`      | `postgresql+asyncpg://timesheet:timesheet@localhost:5432/timesheet` | БД (в compose подставляется адрес контейнера `postgres`) |
| `BOT_TOKENS`        | пусто        | Токены ботов через запятую. Пусто — сервис работает без Telegram (только API и воркеры) |
| `ADMIN_TOKEN`       | —, обязательна | Значение заголовка `X-Admin-Token` для всех ручек, кроме `/health` |
| `WORKERS`           | `2`          | Число воркеров обработки в процессе (`0` — не обрабатывать очередь) |
| `BATCH_SIZE`        | `100`        | Сообщений в одной пачке воркера |
| `POLL_INTERVAL`     | `1.0`        | Пауза воркера при пустой очереди, секунд |
| `LOG_LEVEL`         | `INFO`       | Уровень логирования |
| `TEST_DATABASE_URL` | `postgresql+asyncpg://timesheet:timesheet@localhost:5432/timesheet_test` | БД для интеграционных тестов |

## Настройка бота

1. Создать бота у [@BotFather](https://t.me/BotFather), токен положить в `BOT_TOKENS`.
2. **Отключить privacy mode** (в BotFather: `/setprivacy` → бот → Disable) **или сделать бота администратором
   группы**. Иначе Telegram не присылает боту обычные сообщения группы и фото он не увидит. Если бот уже был
   в группе до смены настройки, его нужно удалить из группы и добавить заново.
3. Добавить бота в рабочие группы и зарегистрировать каждую группу через `POST /groups` (её `chat_id` можно
   взять из журнала: сообщения незарегистрированных групп сохраняются со статусом `rejected/unknown_group`).

Несколько ботов поддерживаются: один Dispatcher поллит все токены. Если в группе несколько ботов, одно сообщение
придёт несколько раз — дубль отсекается уникальностью `(chat_id, message_id)`.

Фото нужно отправлять как фото. Картинка, отправленная файлом (без сжатия), молча игнорируется и в журнал
не попадает. Ссылки на сообщения в журнале есть только у супергрупп (`chat_id` вида `-100…`); у обычной группы
поле `link` пустое, остальное работает так же.

## Примеры (curl)

```bash
H='X-Admin-Token: change-me'; J='Content-Type: application/json'

# Группа: окно отметки 07:00–10:00 по Москве (tz по умолчанию Europe/Moscow).
# Окно через полночь задаётся как start > end, например 20:00–08:00. POST повторно — обновление.
curl -X POST localhost:8000/groups -H "$H" -H "$J" \
  -d '{"chat_id": -1001234567890, "title": "Пост 1", "window_start": "07:00", "window_end": "10:00"}'

# Сотрудники: фамилия для сопоставления — первое слово ФИО или явно через "surname"
curl -X POST localhost:8000/employees -H "$H" -H "$J" -d '{"full_name": "Мехоношин Алексей Петрович"}'
curl -X POST localhost:8000/employees -H "$H" -H "$J" -d '{"full_name": "Иванов Иван"}'
curl -X POST localhost:8000/employees -H "$H" -H "$J" -d '{"full_name": "Иванов Пётр"}'

# Привязка Telegram-аккаунта к сотруднику. tg_user_id автора — поле tg_user_id в журнале (GET /messages)
curl -X PUT localhost:8000/bindings/555000111 -H "$H" -H "$J" -d '{"employee_id": 3}'

# Журнал обработки (фильтры: status, employee_id, shift_date; пагинация limit/offset)
curl "localhost:8000/messages?status=accepted&limit=20" -H "$H"
curl "localhost:8000/messages?employee_id=1&shift_date=2025-09-19" -H "$H"   # история по сотруднику и дате

# Ручная проверка: id сообщения — поле "id" из GET /review (не message_id из Telegram)
curl localhost:8000/review -H "$H"
curl -X POST localhost:8000/review/3/approve -H "$H" -H "$J" -d '{"employee_id": 2}'   # shift_date — опционально
curl -X POST localhost:8000/review/4/reject -H "$H"

# Табель за месяц (по всем группам или по одной)
curl -o timesheet-2025-09.xlsx "localhost:8000/timesheet?month=2025-09" -H "$H"
curl -o post1-2025-09.xlsx "localhost:8000/timesheet?month=2025-09&chat_id=-1001234567890" -H "$H"
```

Пример из ТЗ: фото с подписью «Мехоношин» в 08:50 19.09.2025 по Москве в группе с окном 07:00–10:00 даёт
`accepted/by_caption` и `1` в колонке «19» строки «Мехоношин Алексей Петрович».

## Поток сообщения

```
 Telegram ──getUpdates──▶ aiogram Dispatcher (все BOT_TOKENS)
                              │  только фото в group/supergroup
                              ▼
                       IngestService ── INSERT … ON CONFLICT (chat_id, message_id) DO NOTHING
                              │          (повторы при недоступной БД)
                              ▼
                  ┌─────── messages (status = new) ───────┐   ← очередь в Postgres
                  ▼                                       ▼
            worker 1 … WORKERS:  SELECT … WHERE status='new' ORDER BY id LIMIT BATCH_SIZE FOR UPDATE SKIP LOCKED
                  │
                  │  одна транзакция на пачку:
                  │   1. справочники: группы, привязки, сотрудники
                  │   2. decide() — чистая функция: группа → окно/дата смены → сотрудник
                  │   3. accepted → INSERT attendance … ON CONFLICT (employee_id, shift_date) DO NOTHING
                  │                 (конфликт → duplicate); отметки ставятся в порядке (employee_id, shift_date)
                  │   4. итоговый статус и причина в messages; ошибка одного сообщения → savepoint, status=error
                  ▼
     attendance ──▶ GET /timesheet (xlsx)        messages ──▶ GET /messages, GET /review → approve / reject
```

Слои: `handlers` (Telegram, HTTP, воркер) → `services` (сценарии) → `domain` (сущности, правила, `decide()`,
интерфейсы репозиториев и Unit of Work в виде Protocol). `repositories` (SQL, ORM, Unit of Work) реализуют эти
интерфейсы; сервисы от них не зависят — реализации подставляются в `app/main.py`. Правила импортов между слоями
проверяются тестом `tests/test_layers.py`.

## Статусы и причины

| Статус | Причина (`reason`) | Когда |
|---|---|---|
| `new` | — | Сообщение принято ботом и ждёт воркера |
| `accepted` | `by_caption` | Фамилия из подписи однозначно указывает на сотрудника, аккаунт не привязан (или привязан к неактивному сотруднику) |
| `accepted` | `by_caption_and_account` | Фамилия и привязка аккаунта указывают на одного сотрудника (в т.ч. выбор среди однофамильцев) |
| `accepted` | `by_account` | Фамилии в подписи нет (или подписи нет), но аккаунт привязан к сотруднику |
| `accepted` | `manual_approved` | Оператор подтвердил спорное сообщение, отметка с `manual = true` |
| `duplicate` | `already_marked` | У сотрудника уже есть отметка на эту дату (повторное фото, approve на занятую дату) |
| `manual_review` | `multiple_employees` | В подписи две и более разные фамилии |
| `manual_review` | `ambiguous_surname` | Фамилия у нескольких сотрудников, привязка не помогает выбрать |
| `manual_review` | `caption_account_mismatch` | Фамилия указывает на одного сотрудника, а аккаунт привязан к другому |
| `manual_review` | `employee_not_found` | Подпись есть, но фамилия не найдена, аккаунт не привязан |
| `manual_review` | `no_caption` | Подписи нет, аккаунт не привязан, сообщение не из альбома |
| `rejected` | `unknown_group` | Группа не зарегистрирована или неактивна |
| `rejected` | `outside_window` | Фото вне окна отметки группы |
| `rejected` | `album_part_without_caption` | Часть альбома без подписи и без привязки аккаунта |
| `rejected` | `manual_rejected` | Оператор отклонил спорное сообщение |
| `error` | `processing_error: <ошибка>` | Исключение при обработке этого сообщения (пачка при этом не страдает) |

У `manual_review` всегда сохранена рассчитанная `shift_date`, у `duplicate` — сотрудник и дата (видно в истории).

## Принятые допущения

**Дата и окно смены**
- Окно задаётся на группу в её таймзоне. `start < end` — окно в пределах суток, дата смены = местная дата.
  `start > end` — окно через полночь: после `start` — смена текущей даты, до `end` — смена предыдущей
  (фото в 06:00 1-го числа при окне 20:00–08:00 попадает в табель прошлого месяца). `start == end` запрещено.
- Время сравнивается с точностью до минуты, обе границы включительно (окно до 10:00 принимает 10:00:59).
- Используется время публикации сообщения в Telegram (`message.date`), а не время получения ботом.

**Определение сотрудника**
- Подпись разбивается на слова (буквы, дефис внутри слова; регистр и `ё/е` не важны, цифры, эмодзи и
  пунктуация игнорируются); фамилия ищется только точным совпадением. Склонения («Мехоношина») не распознаются →
  ручная проверка.
- Неактивные сотрудники не находятся по подписи, привязка аккаунта к неактивному сотруднику игнорируется.
- От анонимного администратора группы или от имени канала Telegram присылает служебного автора
  (`@GroupAnonymousBot` / `Channel_Bot`); его id сохраняется как `tg_user_id`. Привязать такой аккаунт к конкретному
  сотруднику нельзя, поэтому такие фото определяются только по подписи.
- Учитываются только фото (`photo`). Картинка, отправленная файлом, и правки сообщений не обрабатываются и в журнал
  не попадают.

**Обработка и журнал**
- Сообщение с ошибкой обработки получает `error` и автоматически не переобрабатывается (чтобы не зацикливаться);
  сбой всей пачки (например, потеря соединения с БД) откатывает её, сообщения остаются `new` и обрабатываются
  повторно.
- Если два воркера одновременно ставят отметку одному сотруднику на одну дату, отметку получает транзакция,
  закоммитившаяся первой; вторая получает `duplicate`. Внутри пачки отметку получает более раннее сообщение.
- Approve/reject возможны только для `manual_review` (иначе 409); одновременные решения двух операторов по одному
  сообщению не проходят оба (блокировка строки). Approve неактивного сотрудника → 422.
- Справочники (группы, привязки, сотрудники) воркер перечитывает на каждую пачку, так что изменения действуют
  со следующей пачки. Уже обработанные сообщения не пересматриваются: фото, пришедшее до регистрации группы,
  остаётся `rejected / unknown_group`.

**Табель**
- Строки — по алфавиту ФИО. Без `chat_id`: все активные сотрудники и уволенные, у кого есть отметки в месяце.
  С `chat_id`: только сотрудники с отметками в этой группе (привязки «группа → сотрудники» нет).
- Формат по образцу листа «Табель»: «Ф.И.О.», дни 1–31, «кол. смен» = `SUM` по строке, «ИТОГ:» = `SUM` по
  столбцам; шрифт Arial (в образце Times New Roman — по требованию заказчика заменён); несуществующие дни месяца
  залиты серым; заголовок месяца в B1:AG1.
- Формулы сохраняются без вычисленных значений: Excel и LibreOffice пересчитают их при открытии, а превью без
  пересчёта (Quick Look, предпросмотр в мессенджерах) покажут нули в «кол. смен» и «ИТОГ:».

**Надёжность приёма**
- aiogram подтверждает апдейт Telegram до завершения хендлера, поэтому при недоступной БД сохранение повторяется
  с паузами ~2 минуты суммарно. Если БД недоступна дольше или процесс упал во время повторов, событие теряется,
  а его данные пишутся в лог (`ingest gave up, message lost`). Полное решение — webhook (см. «Масштабирование»).
- Невалидный токен в `BOT_TOKENS` останавливает поллинг всех ботов процесса (aiogram проверяет все токены разом),
  ошибка пишется в лог; HTTP API и воркеры продолжают работать.

## Ответы на открытые вопросы (раздел 16 ТЗ) — как допущения

| Вопрос | Принятое допущение |
|---|---|
| В каком виде существует таблица смен | Источник истины — таблица `attendance` в Postgres; Excel-табель по образцу листа «Табель» выгружается за любой месяц. Запись в Google Sheets — вне первой версии |
| Как человек определяет сотрудника по фото и подписи | По фамилии в подписи (как в примере «Мехоношин»). Дополнительно — привязка Telegram-аккаунта к сотруднику; фото не анализируется |
| Единый шаблон подписи или свои правила | Шаблон не требуется: фамилия ищется среди всех слов подписи, во всех группах одинаково |
| Только факт выхода или опоздания, замены, досрочный уход | Только факт выхода (`1`). Фото вне окна — `rejected/outside_window`, отдельных статусов опоздания и замены нет |
| Привязка к объекту, посту, маршруту | Группа = объект/пост: у каждой группы своё окно и таймзона. Отдельной сущности объекта нет |
| Допустима ли полностью автоматическая постановка 1 | Да, во всех группах, но только в однозначных случаях; всё спорное — на ручную проверку |
| Хранить фото или достаточно ссылки | Достаточно ссылки и метаданных: фото не скачиваются, в журнале ссылка `https://t.me/c/<id>/<message_id>` (для супергрупп) |

## Что осознанно не сделано

- Fuzzy-поиск фамилий, склонения, распознавание по имени/позывному/табельному номеру.
- Обработка правок и удаления сообщений после обработки.
- UI (только HTTP API + Swagger), ответы и реакции бота в чате, запись в Google Sheets, хранение фото.
- Роли и права кроме одного админ-токена; авторство ручных решений не сохраняется.
- Привязка к объектам охраны и групп к ограниченному перечню сотрудников.
- Правка и деактивация сотрудников через API, удаление групп и привязок (поле `active` в модели есть).
- Ручное переопределение `rejected` (например, позднего выхода), возврат `error` в очередь и повторная обработка
  сообщений после изменения справочников.
- Миграции Alembic (схема создаётся `create_all` при старте), нагрузочные тесты, метрики.

## Масштабирование

- **Нагрузка ТЗ** (200 групп × тысячи фото в сутки — сотни тысяч сообщений в сутки и больше) рассчитана на очередь
  в Postgres: приём — один `INSERT`, обработка — пачками по `BATCH_SIZE` с частичным индексом по `status='new'`.
  Пропускная способность растёт числом воркеров (`WORKERS`) и реплик. Нагрузочно это не проверялось.
- **Несколько реплик.** Воркеры безопасно работают параллельно в любом числе процессов: `FOR UPDATE SKIP LOCKED`
  раздаёт непересекающиеся пачки, уникальные индексы и единый порядок вставки отметок исключают дубли и deadlock.
  Приём идемпотентен, поэтому повторная доставка безопасна.
- **Один поллер на токен.** Telegram не позволяет двум процессам одновременно делать `getUpdates` с одним токеном
  (409 Conflict). При нескольких репликах `BOT_TOKENS` задаётся только одной (или токены делятся между репликами),
  остальные запускаются с пустым `BOT_TOKENS` — только API и воркеры. Можно и разделить роли:
  `WORKERS=0` для реплик только с API.
- **Webhook вместо long polling** — следующий шаг для продакшена: несколько реплик за балансировщиком принимают
  апдейты, а Telegram повторяет доставку, пока не получит 200 (сохранение в БД до ответа закрывает риск потери
  события из раздела «Надёжность приёма»).
- Дальше: кэш справочников в воркере, партиционирование/архивирование `messages`, Alembic, метрики очереди.
