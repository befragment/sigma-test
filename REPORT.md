# Отчёт о выполнении тестового задания

**Репозиторий:** <ССЫЛКА НА РЕПОЗИТОРИЙ>

**Задача:** система автоматического заполнения табеля смен по фото из рабочих Telegram-групп
(ТЗ — [`docs/task.xlsx`](docs/task.xlsx)).

## Коротко

- Бот (aiogram 3, long polling, несколько токенов) принимает фото из групп и без потерь кладёт их в очередь
  в Postgres. Воркеры определяют сотрудника и дату смены и ставят `1` в табеле.
- Спорные случаи (однофамильцы, несколько фамилий, нет подписи, подпись не совпадает с аккаунтом) не ставят `1`
  автоматически, а уходят на ручную проверку: оператор подтверждает или отклоняет через API.
- Каждое фото из группы попадает в журнал со статусом, причиной, датой смены и ссылкой на первоисточник.
  Повторная доставка и повторная обработка не создают дублей.
- Табель за месяц выгружается в xlsx в формате листа «Табель» из ТЗ: дни 1–31, `SUM` по строкам и «ИТОГ:».
- **208 автотестов**, все зелёные. **Проверка на реальном боте и группе Telegram — 13 сценариев из 13**
  ([отчёт](docs/telegram-test-report.md)).

## Как проверить за 5 минут

```bash
cp .env.example .env              # ADMIN_TOKEN — любой; BOT_TOKENS можно оставить пустым
docker compose up -d --build      # app :8000 + postgres :5432
curl localhost:8000/health        # {"status":"ok"}
```

Справочники и запросы — по curl-примерам из [README](README.md#примеры-curl) или через Swagger
(http://localhost:8000/docs, заголовок `X-Admin-Token`). Без бота приход фото можно имитировать вставкой в очередь —
ровно это делает Telegram-хендлер. Сначала создай группу `-1001234567890` и сотрудника «Мехоношин» по примерам из
README, затем:

```bash
docker compose exec -T postgres psql -U timesheet -d timesheet -c "
  INSERT INTO messages (chat_id, message_id, tg_user_id, caption, sent_at)
  VALUES (-1001234567890, 101, 900, 'Мехоношин', '2025-09-19 08:50:06+03');"
# через ~1 с: GET /messages → accepted / by_caption, GET /timesheet?month=2025-09 → 1 в колонке «19»
```

Тесты (интеграционные идут на Postgres из compose и пропускаются, если он недоступен):

```bash
python3.12 -m venv .venv && .venv/bin/pip install -e ".[dev]" && .venv/bin/pytest -q
```

Чтобы проверить с настоящим ботом: токен от @BotFather в `BOT_TOKENS`, privacy mode выключен (`/setprivacy` →
Disable), бот добавлен в группу — подробно в [README](README.md#настройка-бота).

## Требования ТЗ и как они закрыты

| Раздел ТЗ | Требование | Решение |
|---|---|---|
| 4.1–4.2 | Обрабатывать только фото, учитывать подпись и время | Хендлер реагирует только на `photo` в группах и супергруппах. Решение принимает чистая функция `decide()`: группа → окно и дата смены → сотрудник |
| 4.3, 8.2 | Повторная обработка не дублирует отметку, дубль фиксируется в журнале | `UNIQUE (chat_id, message_id)` на приёме, `UNIQUE (employee_id, shift_date)` на отметке, вставки через `ON CONFLICT DO NOTHING`. Конфликт даёт статус `duplicate` |
| 6 | Однозначное сопоставление; если неоднозначно — без `1`, с отдельным статусом | Фамилия из подписи (точное совпадение, без учёта регистра и `ё/е`) и привязка Telegram-аккаунта к сотруднику. Все неоднозначные случаи → `manual_review` с причиной |
| 7 | Фактическое время, смены около полуночи, настраиваемое окно по объекту | Окно и таймзона задаются на группу. Окно через полночь (`20:00–08:00`) относит утро к смене предыдущего дня. Вне окна — `rejected / outside_window` |
| 8.1 | Цифровой аналог табеля, ручные правки для уполномоченных | Таблица `attendance` и выгрузка xlsx. Ручные отметки — через approve на ручной проверке (`manual = true`) |
| 9 | Правило или ручная проверка для каждой нестандартной ситуации | 16 пар «статус / причина» — таблица в [README](README.md#статусы-и-причины) |
| 10 | Журнал всех сообщений, причина, первоисточник, история по сотруднику и дате | `GET /messages` с фильтрами `status`, `employee_id`, `shift_date` и ссылкой `t.me/c/…` (у супергрупп) |
| 11 | 200 групп, тысячи фото в сутки, без потерь, очередь | Очередь в Postgres: `FOR UPDATE SKIP LOCKED`, N воркеров и реплик. Ошибка одного сообщения изолирована savepoint-ом. При недоступной БД приём повторяется |
| 12, 13 | Роли, настройки | Справочники групп, окон, сотрудников и привязок — через API. Роли упрощены до одного админ-токена |
| 16 | Открытые вопросы | Ответы оформлены как допущения в [README](README.md#ответы-на-открытые-вопросы-раздел-16-тз--как-допущения) |
| 17 | Критерий приёмки | Автоматический приём, корректное определение, `1` в табеле, нет неконтролируемых дублей, основание каждой отметки — в журнале. Подтверждено автотестами и живой проверкой |

## Архитектура

Один сервис: FastAPI + aiogram + фоновые воркеры в одном процессе, Postgres, `docker compose`. Слои:
`handlers` (Telegram, HTTP, воркер) → `services` (сценарии) → `domain` (сущности, правила, `decide()`, интерфейсы).
`repositories` (SQL, ORM, Unit of Work) реализуют интерфейсы домена. Правила импортов между слоями проверяются
тестом. Схема потока сообщения — в [README](README.md#поток-сообщения).

## Что стоит отметить

- **Найден и исправлен deadlock между воркерами.** Если пачки двух воркеров содержали одних и тех же сотрудников
  в разном порядке, транзакции блокировали друг друга на уникальном индексе табеля. Postgres обрывал одну из них,
  и сообщение ошибочно получало `error`. Тест с барьером детерминированно воспроизводит эту ситуацию. Исправлено единым порядком
  вставки отметок `(employee_id, shift_date)`.
- **Потеря событий при сбое БД.** aiogram подтверждает апдейт Telegram до завершения хендлера, поэтому приём
  повторяется с нарастающей паузой (~2 мин суммарно), а не теряет сообщение сразу.
- **Изоляция ошибок.** Ошибка в одном сообщении откатывает только его (savepoint) — пачка обрабатывается дальше.
- **Ручная проверка конкурентно безопасна.** Строка сообщения блокируется: два одновременных решения по одному
  сообщению не проходят оба (проверено тестом).
- Ключевые гарантии проверены мутационно: без `SKIP LOCKED`, savepoint, блокировки строки или фильтра типа чата
  соответствующие тесты падают.

## Проверка в реальном Telegram

Тестовая группа с ботом (второй бот подключён только для проверки поллинга нескольких токенов), 14 фото
(включая альбом из трёх) и одно текстовое сообщение. Проверены все ветки определения сотрудника, дубли, альбом,
привязка аккаунта, окно смены, ручная проверка (approve, reject, 409 на повторное решение) и выгрузка табеля.
Во время теста дважды обрывалось соединение с Telegram — бот переподключился сам, сообщения не потерялись.
Полный отчёт со скриншотами, журналом и табелем — [docs/telegram-test-report.md](docs/telegram-test-report.md).

## Ограничения первой версии

- Только точное совпадение фамилии, без склонений и fuzzy-поиска. Фото, отправленные файлом, и правки сообщений
  не обрабатываются.
- Бот молчит в чате — результат виден только через API. UI нет, роли сведены к одному админ-токену.
- Схема создаётся `create_all` при старте вместо миграций. Нагрузочного тестирования не было.
- Если БД недоступна дольше ~2 минут, сообщение может потеряться (его данные остаются в логе). Полное решение —
  webhook вместо long polling.
- Полный список с обоснованием — в [README](README.md#что-осознанно-не-сделано).
