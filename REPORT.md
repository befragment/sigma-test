# Табель смен по фото из Telegram — отчёт о выполнении тестового задания

**Задача:** система автоматического заполнения табеля смен по фото из рабочих Telegram-групп. Фото с подписью,
опубликованное в рабочем чате в момент заступления на смену, означает отметку `1` в табеле на дату смены.

**Тестовая группа Telegram:** [https://t.me/+_FgxjlAhGlI2Mjcy](https://t.me/+_FgxjlAhGlI2Mjcy) — здесь можно
посмотреть сообщения, на которых проводилась проверка на реальном боте (раздел 6).

## 1. Результат

- Сервис принимает фото из рабочих групп через Telegram-бота и без потерь ставит их в очередь. Затем определяет
  сотрудника и дату смены и проставляет `1` в табеле.
- Спорные случаи не попадают в табель автоматически: они уходят на ручную проверку, где оператор подтверждает или
  отклоняет отметку.
- Каждое фото фиксируется в журнале со статусом, причиной, датой смены и ссылкой на исходное сообщение. Повторная
  доставка и повторная обработка не создают дублей.
- Табель за месяц выгружается в xlsx в формате листа «Табель» из ТЗ: Ф.И.О., дни 1–31, «кол. смен» и «ИТОГ:»
  с формулами.
- **208 автотестов** проходят. **Проверка на реальном Telegram-боте: 13 сценариев из 13** (раздел 6).
- Поставка: один сервис в Docker Compose (приложение + PostgreSQL) с документацией по запуску, настройке бота и API.

**Стек:** Python 3.12, FastAPI, aiogram 3, PostgreSQL, SQLAlchemy 2 (async), openpyxl, pytest.

## 3. Как работает система

### 3.1. Архитектура

Один сервис: FastAPI, aiogram 3 и фоновые воркеры в одном процессе, PostgreSQL. Код разделён на слои, зависимости
направлены только вниз, правила импортов между слоями проверяются автотестом:

| Слой | Содержимое |
|---|---|
| `handlers` | Точки входа: Telegram-бот, HTTP API, воркер очереди |
| `services` | Сценарии: приём, обработка, справочники, ручная проверка, табель |
| `domain` | Сущности и правила без ввода-вывода, включая `decide()`; интерфейсы репозиториев |
| `repositories` | SQL и Unit of Work — реализация интерфейсов домена |

HTTP API: группы, сотрудники, привязки аккаунтов, журнал сообщений, ручная проверка, выгрузка табеля, `health`.
Все методы, кроме `health`, защищены админ-токеном. Документация API — Swagger.

### 3.2. Поток сообщения

```
 Telegram ──▶ aiogram Dispatcher (все боты одним процессом)
                  │  только фото в группах и супергруппах
                  ▼
           Приём ── INSERT … ON CONFLICT (chat_id, message_id) DO NOTHING
                  │  (повторы при недоступной БД)
                  ▼
           messages (status = new) — очередь в PostgreSQL
                  │
     воркеры ─────┤  SELECT … WHERE status = 'new' ORDER BY id LIMIT … FOR UPDATE SKIP LOCKED
                  │
                  │  одна транзакция на пачку:
                  │   1. справочники: группы, привязки, сотрудники
                  │   2. decide(): группа → окно и дата смены → сотрудник
                  │   3. accepted → INSERT attendance … ON CONFLICT (employee_id, shift_date) DO NOTHING,
                  │      конфликт → duplicate
                  │   4. итоговый статус и причина; ошибка одного сообщения → savepoint, status = error
                  ▼
     attendance ──▶ табель (xlsx)          messages ──▶ журнал, ручная проверка → approve / reject
```

### 3.3. Статусы и причины

| Статус | Причина | Когда |
|---|---|---|

| `accepted` | `by_caption` | Фамилия из подписи однозначно указывает на сотрудника |
| `accepted` | `by_caption_and_account` | Фамилия и привязка аккаунта указывают на одного сотрудника (в т.ч. выбор среди однофамильцев) |
| `accepted` | `by_account` | Фамилии в подписи нет (или подписи нет), но аккаунт привязан к сотруднику |
| `accepted` | `manual_approved` | Оператор подтвердил спорное сообщение, отметка с `manual = true` |
| `duplicate` | `already_marked` | У сотрудника уже есть отметка на эту дату |
| `manual_review` | `multiple_employees` | В подписи две и более разные фамилии |

| `manual_review` | `employee_not_found` | Подпись есть, но фамилия не найдена, аккаунт не привязан |

### 3.4. Правила определения даты смены и сотрудника

**Дата смены.** Окно отметки и таймзона задаются для каждой группы (по умолчанию Europe/Moscow).

- Окно в пределах суток (например, `07:00–10:00`): дата смены — местная дата публикации.
- Окно через полночь (например, `20:00–08:00`): после начала окна — смена текущей даты, до конца окна — смена
  предыдущей. Фото в 06:00 1-го числа относится к смене последнего дня прошлого месяца.
- Используется время публикации сообщения в Telegram, обе границы окна включительно, с точностью до минуты.
- Фото вне окна отклоняется (`outside_window`).

**Сотрудник.**

- Подпись разбивается на слова без учёта регистра, `ё/е`, цифр, эмодзи и пунктуации, двойные фамилии
  поддерживаются. Фамилия ищется точным совпадением по справочнику активных сотрудников.
- Дополнительно учитывается привязка Telegram-аккаунта автора к сотруднику: она позволяет отметить фото без подписи
  и выбрать сотрудника среди однофамильцев.
- Если подпись и привязка противоречат друг другу, найдено несколько сотрудников или не найдено ни одного,
  сообщение уходит на ручную проверку с рассчитанной датой смены.

**Ручная проверка.** Оператор подтверждает спорное сообщение, указывая сотрудника (и при необходимости дату смены),
или отклоняет его. Повторное решение по тому же сообщению отклоняется (HTTP 409).

## 4. Надёжность

- **Без дублей при параллельной обработке.** Несколько воркеров и реплик получают непересекающиеся пачки
  (`SKIP LOCKED`). Отметки ставятся в едином порядке `(employee_id, shift_date)`, что исключает взаимоблокировки
  между транзакциями. Интеграционный тест «2 воркера × 200 сообщений»: каждое сообщение обработано ровно один раз.
- **Ошибка одного сообщения не влияет на остальные.** Его изменения откатываются savepoint-ом, сообщение получает
  статус `error` с текстом ошибки, пачка обрабатывается дальше.
- **Сообщения не теряются при кратковременной недоступности БД.** Приём повторяется с нарастающей паузой.
- **Ручная проверка безопасна при работе нескольких операторов.** Решение по сообщению принимается под блокировкой
  строки: два одновременных решения не проходят оба.
- **Масштабирование.** Число воркеров и реплик настраивается; приём идемпотентен, поэтому повторная доставка
  безопасна. Следующий шаг для продакшена — приём через webhook вместо long polling.
- Ключевые гарантии проверены мутационно: если убрать `SKIP LOCKED`, savepoint, блокировку строки или фильтр типа
  чата, соответствующие тесты падают.

## 7. Ответы на открытые вопросы ТЗ (раздел 16)

| Вопрос | Принятое решение |
|---|---|
| В каком виде существует таблица смен | Источник истины — табель в PostgreSQL; Excel-табель по образцу листа «Табель» выгружается за любой месяц, по всем группам или по одной |
| Как человек определяет сотрудника по фото и подписи | По фамилии в подписи (как в примере «Мехоношин»); дополнительно — привязка Telegram-аккаунта к сотруднику |
| Единый шаблон подписи или свои правила | Шаблон не требуется: фамилия ищется среди всех слов подписи, во всех группах одинаково |
| Только факт выхода или также опоздания, замены, досрочный уход | Фиксируется факт выхода (`1`); фото вне окна отметки отклоняется с отдельной причиной |
| Привязка к объекту, посту, маршруту | Группа = объект/пост: у каждой группы своё окно отметки и таймзона |
| Допустима ли полностью автоматическая постановка `1` | Да, в однозначных случаях; всё спорное — на ручную проверку |
| Хранить фото или достаточно ссылки | Достаточно ссылки и метаданных: в журнале хранится ссылка на исходное сообщение, фото не скачиваются |

## 8. Границы первой версии

В соответствии с разделом 15 ТЗ первая версия охватывает минимальный контур:

- обрабатываются фото; изображения, отправленные файлом, и правки сообщений не учитываются;
- сотрудник определяется по фамилии в подписи и по привязке аккаунта, без нечёткого поиска и склонений;
- `1` автоматически ставится только в однозначных случаях, всё спорное выводится на ручную проверку;
- работа оператора ведётся через HTTP API (Swagger), бот в чатах только читает сообщения;
- доступ к API защищён админ-токеном;
- схема базы данных создаётся при старте сервиса, без отдельной системы миграций.
