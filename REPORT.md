# Отчёт о выполнении тестового задания

**Задача:** система автоматического заполнения табеля смен по фото из рабочих Telegram-групп
(ТЗ — [`docs/task.xlsx`](docs/task.xlsx)).

## Результат

- Сервис принимает фото из рабочих групп через Telegram-бота и без потерь ставит их в очередь. Он определяет
  сотрудника и дату смены и проставляет `1` в табеле.
- Спорные случаи не попадают в табель автоматически: они уходят на ручную проверку, где оператор подтверждает или
  отклоняет отметку.
- Каждое фото фиксируется в журнале со статусом, причиной, датой смены и ссылкой на первоисточник. Повторная
  доставка и повторная обработка не создают дублей.
- Табель за месяц выгружается в xlsx в формате листа «Табель» из ТЗ.
- **208 автотестов** проходят. **Проверка на реальном Telegram-боте: 13 сценариев из 13** (раздел
  [«Проверка в реальном Telegram»](#проверка-в-реальном-telegram)).
- Поставка: один сервис в `docker compose` (приложение + PostgreSQL), документация в [README](README.md).

## Архитектура

Один сервис: FastAPI, aiogram 3 и фоновые воркеры в одном процессе, PostgreSQL, `docker compose`.

- `handlers` — точки входа: Telegram-бот, HTTP API, воркер очереди;
- `services` — сценарии: приём, обработка, справочники, ручная проверка, табель;
- `domain` — сущности и правила без ввода-вывода, включая `decide()`;
- `repositories` — SQL и Unit of Work, реализуют интерфейсы домена.

Зависимости направлены только вниз, правила импортов между слоями проверяются тестом. Схема потока сообщения —
в [README](README.md#поток-сообщения).

## Надёжность

- **Без дублей при параллельной обработке.** Несколько воркеров и реплик получают непересекающиеся пачки
  (`SKIP LOCKED`). Отметки ставятся в едином порядке `(employee_id, shift_date)`, что исключает взаимоблокировки
  между транзакциями. Интеграционный тест «2 воркера × 200 сообщений»: каждое сообщение обработано ровно один раз.
- **Ошибка одного сообщения не влияет на остальные.** Его изменения откатываются savepoint-ом, сообщение получает
  статус `error` с текстом ошибки, пачка обрабатывается дальше.
- **Сообщения не теряются при кратковременной недоступности БД.** Приём повторяется с нарастающей паузой.
- **Ручная проверка безопасна при работе нескольких операторов.** Решение по сообщению принимается под блокировкой
  строки: два одновременных решения не проходят оба.
- Ключевые гарантии проверены мутационно: если убрать `SKIP LOCKED`, savepoint, блокировку строки или фильтр типа
  чата, соответствующие тесты падают.

## Границы первой версии

В соответствии с разделом 15 ТЗ первая версия охватывает минимальный контур:

- обрабатываются фото; изображения, отправленные файлом, и правки сообщений не учитываются;
- сотрудник определяется по фамилии в подписи и по привязке аккаунта, без нечёткого поиска и склонений;
- `1` автоматически ставится только в однозначных случаях, всё спорное выводится на ручную проверку;
- работа оператора ведётся через HTTP API (Swagger), бот в чатах только читает сообщения;
- доступ к API защищён админ-токеном.

Полный перечень принятых допущений и направлений развития — в [README](README.md).
